# Code Review Quality（代码审查质量门槛）

> AI 审查代码时倾向"感觉不错就 approve"，必须用公式量化四维质量。
> 与通用 Search_Quality 互补——Search_Quality 评检索，本公式评代码。

## §1 核心理念

代码审查三原则：

- **审查不是形式**：每条 diff 都要有依据地判断，不是走个过场贴 LGTM。
- **四维缺一不可**：正确性、安全性、可维护性、性能任何一维塌方都可能导致线上事故。
- **不达标必打回**：分数低于合并门槛必须 Request changes 或 Reject，不得"网开一面"。

## §2 Code_Review_Quality 公式

```
Code_Review_Quality = 0.40 × Correctness + 0.25 × Security
                    + 0.20 × Maintainability + 0.15 × Performance
```

权重之和 = 1.0。正确性权重最高（功能错了一切归零），安全性次之（漏洞可被利用），可维护性影响长期成本，性能影响运行成本。

| 维度 | 含义 | 默认权重 |
|------|------|----------|
| Correctness（正确性） | 逻辑是否实现预期、边界/错误路径是否覆盖、是否有测试兜底 | 0.40 |
| Security（安全性） | 输入是否可信、权限是否校验、密钥/注入是否防护 | 0.25 |
| Maintainability（可维护性） | 命名/职责/注释/复杂度是否让他人能接手 | 0.20 |
| Performance（性能） | 是否引入 N+1、泄漏、不合理复杂度、未释放资源 | 0.15 |

## §3 维度子清单

逐维打分前必须走完对应子清单，缺项不得跳过。

### §3.1 Correctness（正确性）

| 检查项 | 通过标准 |
|--------|----------|
| 逻辑正确 | 变更实现了 PR 描述的意图，无反向逻辑、off-by-one、空操作 |
| 边界覆盖 | 空集合、负数、最大值、并发、超时等边界已处理 |
| 错误处理 | 异常被捕获且有明确处置（日志/降级/重试），不吞异常 |
| 测试覆盖 | 新增/改动逻辑有对应单测，覆盖正常与失败路径 |

### §3.2 Security（安全性）

| 检查项 | 通过标准 |
|--------|----------|
| 输入验证 | 外部输入（用户/接口/配置）经校验与转义后再使用 |
| 权限检查 | 敏感操作有鉴权与越权校验，不依赖客户端隐藏 |
| 密钥处理 | 密钥/token 不入日志、不入代码、不进仓库（.env / 密管系统） |
| 注入防护 | SQL/命令/模板/路径注入使用参数化或白名单，无字符串拼接 |

### §3.3 Maintainability（可维护性）

| 检查项 | 通过标准 |
|--------|----------|
| 命名清晰 | 变量/函数/类型名能表达意图，无 `data`/`tmp`/`x` 等无意义名 |
| 单一职责 | 函数/类只做一件事，无超长函数与上帝对象 |
| 注释充分 | 复杂逻辑、非显然决策、外部约束有注释，不解释语法 |
| 复杂度合理 | 圈复杂度可控，嵌套层数合理，无明显可读性陷阱 |

### §3.4 Performance（性能）

| 检查项 | 通过标准 |
|--------|----------|
| 无 N+1 查询 | 循环内不重复查询 DB/远程，已用批量或缓存 |
| 无内存泄漏 | 订阅/句柄/大对象在生命周期结束处释放，无循环引用 |
| 合理算法复杂度 | 数据量级与复杂度匹配，无热点路径上的 O(n²) |
| 资源释放 | 文件/连接/锁/事务在异常路径也能释放（with/finally） |

## §4 维度评分规则

每维按子清单通过情况在 0.0–1.0 间打分：

| 维度分值 | 含义 | 判定标准 |
|----------|------|----------|
| 1.0 | 全部通过 | 子清单全部通过，无隐患 |
| 0.5 | 部分通过 | 过半项通过，存在需修复但不阻断的小问题 |
| 0.0 | 严重问题 | 存在阻断级缺陷（逻辑错误/安全漏洞/崩溃风险） |

> 介于两档之间时按线性插值取 0.25 / 0.75 等中间值，但 0.0 仅用于"严重问题"，不可因"轻微"降为 0.0。

## §5 阈值与处置

| Code_Review_Quality | 处置 | 说明 |
|---|---|---|
| ≥ 0.85 | Approve | 可合并，附四维分数与简要说明 |
| 0.60 – 0.85 | Approve with comments | 可合并但必须留整改意见，跟踪后续修复 |
| 0.40 – 0.60 | Request changes | 必须修改后重新审查，不得合并 |
| < 0.40 | Reject | 严重缺陷，关闭 PR 或要求重写 |

> 任一维度为 0.0 时，无论总分多少，强制降至 Request changes 及以下——单点塌方不得用其他维度高分掩盖。

## §6 检查流程

```
1. 读 diff 理解变更   —— 通读 diff 与 PR 描述，明确意图、影响范围、上下文
2. 逐维走子清单       —— 按 §3.1–§3.4 逐项核对，记录通过/失败/存疑
3. 每维打分           —— 依 §4 规则给四维各打 0.0–1.0
4. 加权算总分         —— 代入 §2 公式得 Code_Review_Quality
5. 对照阈值出决策     —— 依 §5 表给出 Approve / Approve with comments / Request changes / Reject
```

## §7 失败信号

| 失败信号 | 描述 | 修复 |
|----------|------|------|
| 只看正确性忽略安全 | "功能没问题就 approve"，跳过输入验证/权限/密钥检查 | 强制走完四维子清单 |
| 跳过子清单直接 approve | 未逐项核对就贴 LGTM | 强制执行 §6 五步，附四维分数 |
| 严重问题却给 Approve | 存在注入/崩溃/数据丢失风险仍放行 | 单维 0.0 强制降至 Request changes |
| 不算分只写"LGTM" | 未代入公式、无四维分数 | 必须输出每维分数与加权总分 |

## §8 与其他文档的关系

- **`tool-skill-mcp.md`**：审查中需要调用工具（跑测试/lint/静态分析）时按其分工取用 Tool/Skill/MCP。
- **`truth-protocol.md` §8**：Code_Review_Quality 作为 PR 合并置信度的客观输入，分数低即降置信度。
- **`self-refinement.md`**：审查判定为 Request changes / Reject 后触发精炼闭环，修复后重新计算分数。
- **`governance.md`**：高风险变更（鉴权/支付/数据迁移等）即使分数达标也需灰度发布与回滚预案。
